# River Company

**Código-fonte no GitHub; jogo executado localmente. A hospedagem do jogo não está habilitada.**

A TypeScript/Three.js prototype about AI contracts, datacenter upgrades, and a changing river valley.

## Run locally

```sh
npm install
npm run dev
```

Open http://localhost:8017. Vite serves the TypeScript source and reloads it during development. The game is browser-only; it has no backend or saved progress. Use a recent Node.js version that supports running TypeScript tests directly.

## Edit the source

`src/` is the maintained source. `dist/` is generated by the build; do not edit it.

| File                        | Responsibility                                                         |
| --------------------------- | ---------------------------------------------------------------------- |
| `src/core/types.ts`         | Shared game state, contracts, upgrades, and events                     |
| `src/core/economy.ts`       | Prices, reward tiers, production, previews, and environmental costs    |
| `src/core/engine.ts`        | Contract settlement, boosts, purchases, simulation, and endings        |
| `src/rendering/world.ts`    | River valley, wildlife, buildings, camera, and tile selection          |
| `src/rendering/interior.ts` | Server hall and walking workers                                        |
| `src/ui/interface.ts`       | Persistent upgrade cards, contract controls, graph, and click feedback |
| `src/styles.css`            | Responsive interface styling                                           |
| `src/main.ts`               | App startup, input, rendering loop, and wiring between modules         |

TypeScript uses strict checking, unused-code checks, and erasable syntax. Rendering is kept outside the game engine so gameplay rules can be tested without a browser or GPU. Node's built-in test runner verifies rapid boosts, capped payouts, automatic/manual settlement, pauses, capacity bottlenecks, deadlines, and failed purchases.

```sh
npm run typecheck
npm test
npm run build
npm run format
```

`npm run build` generates a local production build. It does **not** deploy. To serve that build, stop the development server and run `npm run preview`.

## Play

Place the datacenter on land, then click anywhere in the game to earn revenue. Each running-game click pays a small base amount, including clicks on interface controls. During an active contract, it also advances work and earns a proportional contract payment. Contract payments never exceed the signed reward; manual click revenue is tracked separately. Panning or scrolling does not earn cash. Pausing stops paid clicks.

The upgrade list stays on the left in both views, with short names, prices, and levels. **Capacity** improves the existing datacenter rather than creating another site. The building grows wider, deeper, and taller through a short construction animation. Its campus reserves room for later expansion, and utility placement avoids that footprint. Solar, petrol, and cooling each occupy one structure and upgrade it on subsequent purchases. Forest restoration still plants trees.

Contracts have 20-, 25-, and 30-second game-time deadlines, with increasing work and rewards. More usable capacity, chips, and automation help finish them. Petrol supplies four additional power units per level; solar supplies two. Petrol is cheaper and offers larger payouts on new contracts, but pollutes. Higher capacity needs sufficient power and cooling. Fossil processing damage remains gradual and is scaled for the shorter jobs.

Three offers appear in the center while choosing. Only the signed contract remains visible beside the sidebar during work; completion or expiry animates the next three offers. Automatic income per second stays at the top beside cash. Idle time alone does not earn revenue.

Click the datacenter to inspect the server hall. Each click also earns money. Clicks also earn inside; upgrades remain available. **Valley** or Escape returns to the map. Drag the valley to pan; scroll to zoom. **C** pays one click. Space pauses. Speed cycles through 1×/3×/6×.

Announcements appear at the top. Text selection, selection callouts, and normal copy gestures are disabled without overwriting the clipboard.

The world uses one applied destruction value for its appearance and destructive ending. Environmental effects queue and transition through intermediate percentages at up to five points per real second, at most one point per update, independent of simulation speed. Colors, canopies, and mutations change gradually. The destructive ending requires 100% damage. The green ending requires 20,000 lifetime earnings and 16 completed contracts, with no active contract, settled pollution and damage below 58%.

At the ending, the HUD fades and the camera pulls back over three seconds, leaving the landscape alone. Escape opens the recap and replay controls; clicking or tapping the final landscape also opens them. Reduced-motion preferences skip the long camera movement.

## Nearby civilization

A reachable district is planned on dry land near the first datacenter. It begins with a footpath and three workers. Investment grows the workforce (up to fifteen), adds an access-road paving crew and machinery, brings a parking lot with cars, and raises three concrete panel housing blocks through scaffolding. Housing appears at investment levels 2, 4, and 6; roads and parking begin with the first upgrade. Investment is the total number of purchased upgrades. Construction uses real-time animation and respects pause.

The settlement is kept separate in `src/rendering/settlement.ts`; land planning and facility dimensions are in `src/rendering/development-layout.ts`. Reserved lots keep utilities and restoration from overlapping homes, parking, roads, and the expanding campus. Clearing vegetation contributes queued environmental damage. Housing and cars darken as the world deteriorates; the workforce disappears by total destruction. Worker demon transformations remain a future feature.

This pass used strict TypeScript checks, a local build, Node-based geometry/progression tests, and an 18-location planning sweep. No Playwright session was used.

Upgrade tuning lives in `src/config/game-balance.ts`: `baseCost` sets the first price, and `growth` multiplies the price for each purchased level. This file also holds contract definitions and the datacenter's starting size and expansion limits. Prices are higher than the earlier prototype, while petrol remains cheaper than renewable energy.

Every upgrade now changes the scene: capacity expands the facility in all dimensions; chips fit additional server cabinets; automation installs control equipment; efficiency adds rooftop heat exchangers; power and cooling grow their respective installations; restoration plants actual trees. Housing uses separate dry lots at least six tiles apart, with bridges and pedestrian routes connecting lots across the river. The larger datacenter snaps inward to a nearby dry footprint to leave space for expansion.

Session length is tuned through `PROGRESSION` in `src/config/game-balance.ts`: the green ending requires 20,000 lifetime earnings and 16 completed contracts, while the destructive ending still requires 100% destruction. Processing pollution and petrol emissions are tuned for shorter prototype sessions, with harmful choices moving the environment faster. `LAND_CLEARING` controls crew speed, concurrency, and the road verge. Roads clear nearby trees and reserve that space against replanting; each cutting animation now takes about 2.2 real seconds with up to ten crews at once.

Contract workloads are now 60 / 160 / 320, with capacity demands of 1 / 4 / 8 and deadlines of 20 / 25 / 30 seconds. Base payouts are 70 / 450 / 1,350, so the larger contracts require more equipment and active clicking to earn their rewards. Tune these in `CONTRACTS` in the balance config.

Each signed contract advances the offer round. Next-round workloads grow by 4.5%, rewards grow by 5.5%, and capacity demand increases every six rounds; deadlines stay short. A signed job keeps its original terms, and a missed deadline still advances the next round. `CONTRACT_PROGRESSION` configures this progression. `CLICK_REVENUE.baseCash` is 1: clicks earn even between contracts or when processing is stalled, and chip/efficiency upgrades increase that revenue. Automatic work still requires an active job and enough power/cooling.

Wildlife is managed in `src/rendering/wildlife.ts`, with counts, habitat preferences, scale, and speed in `src/config/wildlife.ts`. The valley includes capybaras, toucans, agoutis, marmosets, parrots, armadillos, anteaters, frogs, and river fish. Ground animals follow connected dry tiles, birds perch and fly between trees, and fish swim within the river. Nearby tree cutting and new installations trigger faster escape movement. Animals pause between trips, gradually slow and mutate with pollution, and fish disappear from severely polluted water. `world.wildlifeStats()` exposes population counts through the existing development inspector.

Wildlife wandering now varies trip length, route direction, speed, and pauses. Animals remember recent tiles, can escape over road reservations, and widen their search if no route is available. Birds use open landing spots when healthy trees disappear. After the first upgrade, up to two existing settlement workers occasionally chase nearby ground animals with axes; animals flee, and a successful strike leaves a briefly visible fallen body. Worker hunts respect dry-land routes, pause, and the ending. `WILDLIFE_HUNTING` tunes chase frequency and speed. Demon geometry emerges from 72% local damage: birds gain jagged wings, armadillos grow armored spines, anteaters acquire enlarged jaws, marmosets get elongated clawed limbs, frogs develop a broad horned maw, and fish gain spines. Glow, horns, posture, and coloration change gradually. `world.wildlifeHuntingStats()` exposes active hunts and deaths.

Rendering, wildlife, workers, visual effects, interior movement, and regular HUD refresh now share a 24 FPS cap. Set `PERFORMANCE.targetFps` in the balance config to change it. The frame scheduler carries fractional timing across display refreshes, skips rendering catch-up frames, and resets timing when browser visibility changes. Contract processing and deadlines still use elapsed time and the selected game speed; movement cadence no longer rises with game speed.

Camera dragging now anchors a point on the terrain under the pointer and pans by ray/ground-plane intersections. It uses current camera matrices between the 24 FPS renders, accounts for zoom and canvas size, and re-anchors at map limits so reversing direction responds immediately.

Power and cooling shortages now show icon badges above the datacenter, highlight the relevant shop options, and appear inside the server hall. The River upgrade adds four cooling capacity per level by physically excavating a connected river intake and installing a pump. Later purchases carve larger bends and widen channels by up to ten connected tiles. Channel planning protects buildings, reserved housing, roads and bridges; removed habitat adds environmental damage, and wildlife reacts to excavation. Costs are in `UPGRADES.water`, and cooling gain, widening, and habitat impact are in `RIVER_COOLING` in the balance config. Existing cooling remains a separate upgrade. River path planning is isolated in `src/rendering/river-diversion.ts`; warning badges are in `src/rendering/facility-warnings.ts`.

River crossings now use joined arched bridge spans with continuous decks, side rails, bank abutments, and worker walking heights matched to the growing bridge. Shared crossings reuse geometry instead of stacking independent water-tile platforms. Planning and geometry are isolated in `src/rendering/bridges.ts`.

The first River purchase also begins construction of a barrage with concrete towers and a blue sluice panel at the datacenter cooling pipe’s original river endpoint. The solid wall blocks the original river course when construction finishes. Later River purchases expand the channel and pumping equipment. The barrier retains water upstream, lowers nearby downstream water levels, slows downstream fish movement, and adds habitat damage. Construction and water movement respect pause and the ending. Model and flow effects live in `src/rendering/river-barrier.ts`; closure and damage settings live in `RIVER_COOLING`. The existing development inspector includes barrier level, closure, and downstream flow in `world.riverIntakeStats()`.

Repeated River purchases now expand from the whole connected river, including protected existing water, while still protecting dry roads, buildings, housing and barrier banks. The first intake prefers a longer diversion; later levels alternate the direction of new bends and excavate up to ten tiles per purchase. If all reachable land is protected, the existing pump and barrier still upgrade, so River is no longer blocked by a boxed-in intake. Three settlement layouts were checked through six River levels each, with every new water tile connected and no protected dry terrain excavated.

The barrage spans the full river width at the cooling pipe endpoint, with a visible collar aligned to the incoming pipe. The first diverted channel starts at that same water tile. Upgrades keep this attachment fixed rather than rebuilding the pipe toward whichever water tile becomes closest. Pipe endpoints use the datacenter’s actual scene position; replacing a pipe removes and disposes its old geometry. Barrier retention follows the river flow direction.

Barrage siting reserves a bank-to-bank crossing before settlement bridge planning. Bridge clearance is at least three blocks measured between structure edges, including bridge bank approaches and dam towers. The cooling pipe terminates at the middle of that wall. Completing construction blocks the original course and retains upstream water. Backed-up water then spreads into an upstream tributary and reservoir, staying above the wall. `RIVER_COOLING.bridgeClearance` configures the spacing. Three river/settlement layouts passed clearance, full-width coverage, pipe endpoint alignment, stopped-flow and repeat-upgrade checks.

The barrage uses two concrete towers, a reinforced closed blue sluice panel, and an overlapping foundation sealing the riverbed. After it finishes, backed-up water searches for unoccupied ground upstream to expand the reservoir. New channel tiles open progressively, disturbing trees and habitat; occupied roads, housing, and the wall remain protected. The downstream river remains narrow and blocked at the barrage. Blue instanced flow markers move from the barrage intake toward the datacenter through the cooling pipe, and an intake ripple shows collection. These effects keep the 24 FPS loop and respect pause/endings. Spillway timing and pipe flow speed are configurable in `RIVER_COOLING`; pipe visuals are isolated in `src/rendering/cooling-water-flow.ts`.

The older sluice silhouette is restored, with tower caps, lifting machinery, blue panel ribs, and a sealed base. Rivers now occupy a recessed bed with taller earth banks. `RIVER_TERRAIN` tunes bank elevation, riverbed depth, normal water level, high upstream reservoir level, and low downstream level. The completed barrage creates a 0.70-block difference near the wall; spillway water descends gradually toward the downstream channel. Water geometry fills from the fixed riverbed to its current surface instead of floating as thin slabs. Fish and intake ripples follow the new water elevations, while the pipe connection remains aligned.

All River excavation is now restricted to upstream terrain: the first intake, later upgrades, and automatic overflow cannot add water tiles at or below the barrage. Reservoir growth retains the high upstream water level; the lower river keeps its original footprint and lower level.

The barrage foundation now extends below the riverbed and up past the upstream water surface, making a continuous concrete barrier beneath the blue panel. Water tiles at the barrage are split into high upstream and low downstream halves, preventing the reservoir’s water column from appearing as a blue wall below the dam.

The barrage visual now includes tapered concrete abutments, stepped caps, lifting winches, framed steel gate panels, safety markings, a service walkway with rails, a ladder and a water-level gauge. Repeated rail posts, ladder rungs and hazard markings are instanced. The model stays within its existing clearance footprint and retains the sealed foundation, water-level behavior and cooling pipe connection.

Once the barrage finishes, downstream water gradually drains and blends into exposed brown mud. Drying advances away from the wall and takes about 45 real seconds per reach, with a distance delay; pause and endings stop it. The upstream reservoir stays filled, and downstream fish become stranded and die after the bed dries. `RIVER_DRAINAGE` configures duration, propagation delay and mud color; progression is isolated in `src/rendering/river-drainage.ts`.

Drainage now takes 45 seconds plus a distance delay. The first barrage stocks up to six fish downstream; they remain visible and flop as water retreats, die two seconds after their tile fully dries, and leave bodies on the mud for 45 seconds. `STRANDED_FISH` in `src/config/wildlife.ts` configures counts, thresholds, death delay and corpse duration. The development inspector exposes these states through `world.wildlifeFishStats()`.

Terrain configuration is centralized in `src/config/terrain.ts`: map width/depth and seed; river width, bends, offset and color; tree/palm/rock probabilities; the initial clearing; grass/soil colors; riverbed and water elevations; and drying duration/delay/mud color. Use even map dimensions to keep the existing half-block grid centered. Drying is set to 45 seconds; fish stranding/death settings remain in `src/config/wildlife.ts`. Terrain exports from the balance config remain available for compatibility.

### Riverside community

A small fictional Indigenous community is present before construction: three timber/thatch homes, a garden, and nine residents. It does not represent a specific real people. Its footprint is reserved so infrastructure and road planning cannot overlap the homes. Residents walk locally; sustained pollution, nearby forest clearance, and downstream river drying cause illness, slower movement, and staggered deaths. Surviving residents recover when conditions improve; deaths are permanent. Gardens wilt and homes weather as the habitat declines. There are no cash rewards or additional HUD panels for these events.

Tune population, habitat radius, damage thresholds, exposure time, and forest/water stress in `src/config/village.ts`. Models and lifecycle simulation live in `src/rendering/village.ts`; `world.villageStats()` exposes the community's state for local debugging.


### Shorter sessions and continuous environmental progression

The clean ending now requires 16 deliveries and 20,000 lifetime earnings. Processing pollution is 0.024 per work unit and petrol emissions are 0.10 per second per generator; the destructive ending still waits for the same applied 100% damage shown by the world. Destruction smoothing remains five points per real second, at most one percentage point per update.

Canopies start thinning around 18% damage; ground fissures gradually spread from 18%, animal mutations begin at 35%, drifting ash at 42%, demonic forms at 60%, and fires at 65%. Sky and sunlight colors blend continuously. Ground scars, ember fissures, and ash use three instanced draws in `src/rendering/environment-details.ts`; thresholds and population limits live in `src/config/environment.ts`. These effects follow damage and can recede with recovery; no additional announcements or HUD panels are added.

### Optional Fast mode

Use **Fast** beside the pause/speed controls to toggle shorter sessions, including during an existing run. Fast mode gives 3× manual cash, new contract payouts, click work, and automatic work. Processing pollution, emissions, and environmental recovery also receive a 3× multiplier. The clean ending requires eight deliveries and 7,500 lifetime earnings; the destructive ending still requires the full smoothly applied 100% destruction. Contract cooldown drops to two real seconds. Contract deadlines, world animations, and the 24 FPS cap remain unchanged; the separate 1×/3×/6× simulation control still changes simulation time as before. An active contract keeps its signed payout when switching modes. Fast mode starts off on a fresh run. All mode settings live in `src/config/fast-mode.ts`.

Petrol and River upgrades now each add **one** unit of power/cooling (previously four), so each additional server capacity requires another resource purchase when using these options. Solar and sustainable Cooling still add two units per purchase. Prices remain unchanged, preserving the cheaper harmful route. Petrol output is configured in `PETROL_POWER.capacityPerLevel` and River output in `RIVER_COOLING.capacityPerLevel` in `src/config/game-balance.ts`; upgrade descriptions, previews, and fossil power share use those same values.

### Interface em português e guia inicial

Todos os textos voltados ao jogador estão em português brasileiro: menus, melhorias, contratos, avisos, finais, descrições acessíveis e instruções. Valores usam o formato `pt-BR` (por exemplo, `1.234,5`). O nome exibido é Companhia do Rio e o gráfico identifica o valor da empresa como CR.

O tutorial aparece em um cartão destacado no topo, com título, etapa de 1 a 12 e barra de avanço. A orientação permanece até a ação ser concluída; as explicações de trabalho e valor da empresa têm o botão **Entendi**. A conclusão fica visível por quatro segundos e depois desaparece, sem botão para reabrir. Etapas de energia e refrigeração já atendidas são puladas, e o tutorial não recomeça em expansões posteriores. O cartão se adapta a telas menores e respeita a preferência por menos movimento. Os títulos e etapas ficam em `src/config/tutorial.ts` e as instruções em `src/core/tutorial.ts`.
